SAP ABAP · brownfield modernisation

A repeatable way to move legacy ABAP toward S/4HANA Clean Core.

Modernising custom ABAP is mostly mechanical work at large scale: find the unreleased APIs, replace them with released equivalents, restructure to ABAP Cloud, keep the security intact, and verify. The moderniser does that bulk automatically and consistently — offline, grounded on SAP's released-API registry — and asks a person only where the answer genuinely needs judgment.

Built for whole packages, not single objects

This is the part that matters for a real migration backlog: the work scales because a person is needed for the exceptions, not for every object.

The unit of work is the package, not the object. The moderniser freezes one dependency-ordered plan across everything, then builds each object that's ready in parallel — dependencies first, the entry point last.

A person is pulled in only for the genuinely ambiguous: a dependency cycle, a piece of dynamic code whose targets can't be known statically, a security change that needs sign-off. Review effort tracks the number of those exceptions, not the number of objects.

Running offline is what keeps that affordable. A whole package is planned and built without spending a live SAP connection per object — scarce DEV-system time is used only at the end, on the parts a human is releasing. A package of hundreds of objects is the same loop with a wider frontier.

How it works

Four stages, in order. The control flow is deterministic code — the AI writes and evaluates the ABAP; it does not decide the schedule or the verdict.

01

Analyse offline · static

A code-property-graph analyser diagnoses the legacy package — released-API compliance, dependencies, S/4 readiness — and produces a modernisation plan. No system connection; the same engine later re-checks the result.

02

Plan dependency-ordered · frozen

One immutable, bottom-up plan across the whole package. A dynamic-code scan seals any object whose runtime behaviour can't be resolved statically — those wait for a person; they are not guessed.

03

Build loop per object, in parallel

Ground → transform → check. Every proposed API is verified against the released-API registry; the target is written as Clean-Core ABAP Cloud; a rules-based check gates it before it advances. Anything unresolvable is left behind a named seam for a person.

04

Review & release human decides

The run produces modernised objects and the evidence behind them. Offline it never marks an object done — the output is a reviewed draft, and a person releases the transport.

Where a person stays in the loop

The moderniser produces the work and the evidence for it — it does not sign off its own output. Offline it never declares an object finished; a person reviews the draft and releases it.

It also doesn't fill gaps by guessing. The classic blockers weren't hidden — they were replaced with the released successors the registry named, in code the analyser then re-measured:

CALL FUNCTION → released API CL_SALV_TABLE → Fiori Elements T001 → I_CompanyCode SKB1 → I_GLAccountInCompanyCode TBSL → I_PostingKey BSEG → I_OperationalAcctgDocItem

And it reports honestly, even against itself: when the analyser re-scanned the generated code it flagged low cohesion in a few classes the rules-check had passed — a design note worth a reviewer's attention. The point is to hand you a precise, honest to-do list, not a false all-clear.

What it changes, in plain terms

S/4 migration stops being an object-by-object manual effort. The mechanical majority — grounding, transformation, Clean-Core checking — runs automatically and repeatably, and people spend their time on the decisions that actually need them. On abap_fico that meant every S/4 blocker cleared, every unreleased-API use replaced, and a Clean-Core grade of A — from one offline run, with two objects flagged for review.
