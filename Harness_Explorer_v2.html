The thesis

A generator that never grades its own work, behind gates that only tighten

The harness builds the full ABAP Cloud stack — RAP business objects, CDS data models, Fiori Elements apps, and the ABAP classes and unit tests behind them — every object grounded on released APIs and gated before it ships. Five ideas carry the whole design.

The builder never grades its own work

One agent writes the ABAP; a separate, independent reviewer judges it on a real SAP system. The author can't approve, override, or ship its own output — so quality is always verified by someone else, never assumed.

Quality only ever tightens

Every successful run raises the bar and never lowers it — accepted warnings can only shrink, test coverage can only grow, and a quality check that didn't run counts as a failure. The system cannot quietly regress.

The right rigor for the risk

A one-line fix doesn't pay for a full design-and-review pipeline, while a change that touches something sensitive is automatically escalated to the stricter path. Effort scales to the stakes — never more, never less.

A person always releases to production

The harness takes work all the way to activated, proven objects in a development system, with a complete evidence pack — then stops. A person reviews the proof and performs the release. It never connects to production.

Everything runs locally

Three local substrates, all on your own machine: a live connection to SAP, an offline analyser that maps an entire codebase, and a Clean-Core grounding-and-linting engine. No external cloud service sits in the loop.

Offline for scale, live for proof

Analyse and modernise an entire codebase completely offline — no credentials, no connection needed. When you're ready to build and validate against a real system, the same engines run live. Speed and scale offline; hard proof live.

Executive summary

Accelerating the SAP AI journey — Clean-Core delivery, not just code suggestions

SAP's move to S/4HANA Cloud and the Clean Core mandate push every custom object onto ABAP Cloud — released APIs only, RAP, CDS, Fiori. SAP's own AI, Joule, accelerates the developer keystroke-by-keystroke inside the IDE. The AI Harness for SAP goes a step further: it autonomously builds and gates the entire ABAP Cloud object set, so what reaches the transport is Clean-Core Level A, ATC-clean, and test-covered — by construction, not by hope.

What it builds full ABAP Cloud object set

The generator authors, and an independent evaluator gates, every object a modern SAP application needs:

  • RAP Business Objects — managed / unmanaged / draft-enabled behavior definitions + behavior-pool implementation classes; the transactional core of a Fiori app.
  • CDS data model — interface view entities + consumption/projection view entities, always as CDS VIEW ENTITY (never legacy DEFINE VIEW).
  • Fiori Elements apps — the @UI-annotated projection, the service definition + binding (OData V2/V4), and the generated app project (manifest + launchpad) together give a deployable List Report / Object Page with no hand-written UI.
  • ABAP classes + ABAP Unit tests — behavior handlers, consumer classes, and LTCL_* tests mapped to acceptance criteria.
  • Supporting DDIC + sanctioned extensions — tables, and Clean-Core extension via BAdI / RAP / CDS-extend only.

Roadmap — the FSM + grounding pattern is designed to extend to CDS/CAP; CAP is deferred today as a deliberate depth-over-breadth choice.

How it accelerates the AI journey

  • From assist to autonomy — a deterministic scheduler drives a whole dependency-ordered plan across large brownfield estates, not one object per prompt.
  • Enforcement, not suggestion — a fresh-context evaluator renders merge-blocking verdicts against 8 SAP-native gates (ABAP Unit, ATC priority-1 = 0, coverage ratchet, Clean-Core Level A, released-API, invariants, design, diff). The generator can't approve its own work.
  • Quality that only tightens — accepted warnings can only shrink and test coverage can only grow, run after run; the bar never drops.
  • Brownfield at scale — a standalone code-property-graph analyser (blast radius, S/4 readiness, debt) feeds an autonomous modernisation factory that rewrites legacy objects to Clean-Core Level A.
  • Safe by construction — non-prod writes fail closed; a human reads the proof bundle and releases the transport. No PRD connection, ever.

Where it fits

This is AI as a delivery system, not a coding assistant. The harness plans, builds, tests, and gates entire ABAP Cloud applications and brownfield modernisations on its own — then hands a person a release-ready, fully audited transport. It earns its place wherever correctness cannot be left to chance: regulated landscapes, large S/4HANA transformations, and high-volume work that has to be right the first time, at scale, without a developer shepherding every object.

The four engines

Pipelines — analyser · greenfield · moderniser · oracle

Four engines do the heavy lifting: one maps and diagnoses an existing codebase, one builds new applications, one modernises legacy code, and one grounds every decision against SAP's released APIs. Each stands alone and runs offline; all connect to a live system when it's time to prove the work.

Analyser diagnosis brain · offline + live

Parses an abapGit bundle (or live-pulled source) with @abaplint/core, builds an in-memory Code Property Graph, runs ~185 abaplint built-ins plus 16 harness rule packs (154 canonical "TALOS-parity" rules), then scores readiness and emits one schema-validated findings document.

  • Three modes, one engine — analyse_bundle (OFFLINE: parse an abapGit bundle, no MCP, no creds — the deterministic scale path shown in the offline chain); analyse_source_system (LIVE “via-engine”: pull a package’s objects + source from the live sidecar over read-only ADT tools, then build the full CPG locally); analyse_via_adt (LIVE “via-ADT”: run ATC + migration analysis directly on the live system, no local parse — graph/blast are empty in this subset). Both live modes are read-only and run end-to-end in test:live against the real sidecar (no test doubles). Shared transport: callAdtTool from mcp-adt-bridge/adt-client.js.
  • Spine — orchestrator.js › analyzePackage(): canonicalize (LF+sort) → load Registry → build CPG (semantic.js: pass-1 object nodes, pass-2 reference/statement/metadata/RAP edges) → run rules → finding identity + severity + curation → enrich → S/4 readiness + blast radius + debt + modernization plan → writeReport() (fail-closed on schema-invalid).
  • Output — specs/brownfield/analyser-findings.json (schema 1.1.0), the sole engine-to-engine handoff. Plus a hardened HTML report (hash-based CSP, every string escaped — P8) and SARIF 2.1.0.
  • Determinism — byte-identical output; run_id = hash(source_hash + config_hash) is the cache key + provenance.
  • Scale — a hard NFR: enterprise-scale packages (100,000+ lines of ABAP), with a node cap → truncated flag and per-file byte caps.
MCP: analyse_bundle · analyse_source_system · analyse_via_adt · get_report  |  CLI: node analyser/cli.js <bundle> --out … --html …

Greenfield net-new build rail

The "understand → ground → generate → lint" rail for brand-new ABAP Cloud objects, entirely offline. It grounds the generator on released APIs before code is written, and lints the result for Clean-Core Level-A violations after.

  • GF-1 grounding — classifyRef() over the bundled cloudification registry; harvests refs from the brief and returns a released / deprecated / not-to-be-released pack that seeds the generator.
  • GF-2 linter — a 58-rule parser-based ABAP-Cloud linter (KIND_RULES per abaplint constructor + TEXT/statement rules + a P4 invariant pre-screen). errorCount > 0 blocks → regenerate loop.
  • Locked rule — greenfield never imports analyser code; it shares only the @abaplint/core library and the top-level data/ registry.
MCP: ground_released_apis · lint_abap_cloud  |  GF-3 wired into design/implement/validate · GF-4 (live validate) awaits DEV creds

Moderniser brownfield modernisation factory

Consumes the analyser's findings, freezes a content-hashed bottom-up dependency plan (SCC-condensed DAG → Kahn levels/waves), and drives every object through the per-node quality loop toward Clean-Core Level A — under a deterministic scheduler where the CLI owns all control flow.

  • Two modes, one plan — OFFLINE (default): engine-direct, zero MCP/ADT calls, deterministic and byte-reproducible; a full pass rests at PROVISIONAL_GATED (offline never GREENs, P6). LIVE (drive --verdict --live): the engine autonomously runs the DEV push→activate→gate round-trip over the shared callAdtTool, then EARNS GREEN from the system’s own ATC / ABAP-Unit / activation results. P5 fail-closed — no write without HARNESS_ADT_ALLOW_WRITE=1 and a customer-namespace target, refused before any I/O. The transport is still released by a human; live mode stops at a GREEN/BLOCK verdict in DEV.
  • Reducer + driver — a pure copy-on-write reducer (sched/loop.js) and a deterministic stepper (sched/drive.js) that returns the ONE next action; the /modernise skill is a "dumb fulfiller".
  • Per-node gates — SELF_CHECK runs the greenfield 58-rule linter plus the analyser rule-gate (the structural RAP/N+1 rules the linter lacks); the offline verdict then runs the parity and P4-invariant conjuncts on the signed warn-delta, grounded by the idiom knowledge base (rule_id → cause/fix/before→after).
  • GREEN is EARNED, never asserted — the unified verdict is GREEN ⇔ activated ∧ reconciled ∧ atc_p1=0 ∧ atc_p2=0 ∧ unit.green ∧ P4.intact. OFFLINE partitions out the four DEV-only conjuncts and rests at PROVISIONAL_GATED; LIVE supplies them from the DEV round-trip and reaches GREEN. Either way the reducer refuses GREEN without a recorded green verdict — the grader is the SAP system, not the engine.
  • Exceptions — a closed 7-kind escalation taxonomy; a human never grants a machine PASS.

Oracle the grounding authority

The offline "common language": a conservative A/B/C/D clean-core name classifier over two SHA-pinned SAP registries (objectReleaseInfoLatest.json 9.8 MB + objectClassifications_SAP.json). Release-info wins; weakest-wins within. Total by construction — an unlisted name returns unknown, never throws.

  • API — classifyName / gradeUsage / successorOf / debtScore / fixtureFor. Import-only; no CLI.
  • It grounds the modernisation — the design confirms it: MODERNISER_DRIVER_AND_GAP2_DESIGN.md lists the oracle "✅ wired into GROUND — working" (every substitution like T001→I_CompanyCode is oracle-grounded). Its whole job is answering "is this name released? what replaces it?" for the rewrite.
  • How it reaches the moderniser — the analyser node-imports the oracle (curation / enrich / cloudification.js) and bakes the grounding (grade/atc_priority/released_successor) into analyser-findings.json; the moderniser's GROUND step consumes that. The moderniser deliberately does not re-import the oracle offline (cli-park.js: "no registry endpoint to poll — the operator supplies the shipped successor names").
  • Posture — a conservative lower bound, never ground truth: live ATC (P6) is authoritative; the oracle never passes an unreleased API as released.

Nothing unreleased ever gets written

Before a single line of code is generated, every API, table, and CDS entity the harness intends to use is checked against SAP's released-API registry. That check is what makes each object Clean-Core Level A by construction — not by review after the fact.

Substrate #1 · the live-system reach

ADT Integration — the harness's own bridge to live SAP

The harness does not depend on any external copilot for live-system access: it ships its own two-part ADT integration. An MCP front (mcp-adt-bridge) exposes 17 aws_abap_cb_* tools to the agents, and a real ADT REST backend (sap-adt-sidecar) executes them against a live system — the same ABAP Developer Tools services an IDE copilot rides, but driven autonomously by the pipeline rather than typed by a developer. Ported from the TALOS docker/sap-adt adapter, with the reference's fake-success writes replaced by real lock → PUT → activate flows.

mcp-adt-bridge the MCP front

The stdio JSON-RPC 2.0 MCP server wired as the sap-adt entry in .mcp.json. It advertises the 17 tools' input schemas to the agent (tools/list) and forwards tools/call to the sidecar verbatim.

  • P5 write gate — the 5 write tools are blocked unless HARNESS_ADT_ALLOW_WRITE==="1", returning an error before any network I/O.
  • Forwarding — POST {ADT_MCP_URL}/mcp (default 127.0.0.1:8090), passing SAP_* env as X-SAP-* headers.
  • Methods: initialize · tools/list · tools/call · ping.
server.js · adt-tools.js (17-tool registry) · adt-client.js

sap-adt-sidecar the real ADT backend

A Node HTTP service bound to 127.0.0.1:8090 that makes real ADT REST calls. POST /mcp {tool, params} + X-SAP-* credential headers; GET /health.

  • Real session — ADT discovery → basic auth → CSRF fetch → manual cookie jar; authenticates before every tool.
  • Real writes — lock → PUT source/main → activate (no mock mode).
  • P6 fail-closed — quality tools throw on error instead of returning empty/fabricated results.

The control plane

Skills — 24 lanes

Twenty-four workflows that match the effort to the risk. A brand-new build runs the full pipeline — prove SAP doesn't already deliver it, design, build, validate, release. A small change takes a lighter path. And a set of safety routines protect existing code when it has to change: pinning today's behaviour with tests before touching it, keeping refactors behaviour-free, and choosing the safest place to cut. Full ceremony when the risk demands it, never more.

The authoring-time layer

Two tiers run at authoring time, before anything reaches SAP. Enforcement hooks can BLOCK (PreToolUse, exit 2, fail-closed). Advisory hooks only OBSERVE and report (exit 0, always) — telemetry that can never wedge a session. Keeping them apart means exactly one path can veto a write, not two.

Why two tiers, not one

An advisory hook writes what it saw and exits 0 — always; a failure inside it (unwritable state dir, corrupt baseline, malformed input) is swallowed, because telemetry that can wedge a session is worse than none. Two independent paths that could both block would be two sources of truth for “is this allowed” — the divergent-duplication class this codebase has already paid for once. advisory.js is the shared spine; its single exit point cannot choose to block.

RAP behavior (business objects)

How the harness models and generates the RAP business object — the behavior definition (BDEF), the behavior pool implementation class, and the operations/actions/determinations/validations that ride them — and exactly which invariants it holds (AUTHORITY-CHECK, COMMIT ENTITIES) versus what is still roadmap. Every harness claim is grounded in .claude/templates/rap-bo.template.abap, the generator/implement lane, the greenfield linter, and the Gate-7 security reviewer.

Managed vs unmanaged vs draft-enabled — what does the harness default to, and when is unmanaged allowed?
SAP fact: a MANAGED BO lets the RAP runtime own lock/CUD/persistence via the mapped table; an UNMANAGED BO makes you implement READ/LOCK/CUD/save yourself (typically wrapping a legacy API). Draft-enablement (with draft) is orthogonal to both — it adds a draft table plus Edit/Activate/Discard/Resume/Prepare handling for Fiori draft, and can sit on a managed or unmanaged BO. Harness: the RAP-BO template defaults to managed with additional save; + with draft; and comments that you switch to unmanaged 'only if the story requires custom persistence' (rap-bo.template.abap:38-39). The design-critic scores 'unmanaged with no reason' as wrong-paradigm 1–3, so managed is the sanctioned default and unmanaged must be story-justified.
evidence — .claude/templates/rap-bo.template.abap:33,38-39; .claude/agents/abap-design-critic.md:48
Is the behavior definition (BDEF) a separate object from the behavior pool class ZBP_*, and who owns them?
SAP fact: yes — the BDEF is a declarative source object (define behavior for …) that names operations, draft, authorization, field control, mapping, and the implementing class; the behavior pool is an ABAP class (FOR BEHAVIOR OF) whose local handler/saver classes carry the executable logic. Harness: template Part 1 emits the BDEF (rap-bo.template.abap:30-128); Part 2 emits the global class ZBP_I_* … PUBLIC ABSTRACT FINAL FOR BEHAVIOR OF ZI_* (138-146) plus the local handler class inheriting cl_abap_behavior_handler (152-368). The generator treats the BDEF + projection BDEF + behavior class as ONE object group with ONE owner that change together — split ownership is a stop-and-reconcile gotcha.

How are create/update/delete, custom actions, determinations, and validations modelled — and how do they bind to the pool?
In the BDEF: create; update; delete; are the CUD boundary; a custom instance action is action ( features : instance ) acceptEntity result [1] $self;; a save-time derivation is determination setStatus on save { create; field … }; a save-time reject is validation validateEntity on save { create; update; field … }. Each declared op has exactly one matching method in the local handler — FOR MODIFY … FOR ACTION, FOR DETERMINE ON SAVE, FOR VALIDATE ON SAVE, FOR INSTANCE FEATURES, FOR GLOBAL/INSTANCE AUTHORIZATION. Optimistic concurrency is declared with total etag LastChangedAt + etag master LocalLastChangedAt; key numbering is server-owned via field ( numbering : managed ).

How is EML used inside the handlers, and does the harness guard against the classic RAP performance traps?
SAP fact: EML (Entity Manipulation Language) is the ABAP API for RAP entities — READ/MODIFY ENTITIES inside handlers, COMMIT ENTITIES at the transactional boundary — and handlers use IN LOCAL MODE to work inside the BO below the projection/authorization layer. Harness: the determination (setStatus) and the action (acceptEntity) both use READ ENTITIES … IN LOCAL MODE + MODIFY ENTITIES … IN LOCAL MODE (rap-bo.template.abap:188-211,290-303); the validation (validateEntity) uses READ ENTITIES … IN LOCAL MODE then appends to failed/reported — it never MODIFYs, because a validation must not mutate. The determination builds a dedicated update internal table rather than APPENDing into the cursor it loops. The generator is instructed to emit the batched/pre-loaded form from the first line: no MODIFY/READ/COMMIT ENTITIES inside a LOOP (ABAP-PERF-11), no SELECT in loop / N+1 (ABAP-N1), a FOR READ handler never mutates (ABAP-PERF-78), and unbounded EML drivers are IF-guarded (ABAP-PERF-12).

Which invariants does the harness hold on a RAP BO, and by what mechanism — not just declaratively?
P4 invariants: INV-1 AUTHORITY-CHECK never removed/weakened, INV-2 the RAP save (COMMIT ENTITIES) never suppressed, INV-3 SY-SUBRC checked immediately after every AUTHORITY-CHECK. Three enforcement layers back this, not just the template annotations (rap-bo.template.abap:20-23,270-287,320-327): (1) authoring-time refusal — the generator refuses a story instruction to drop AUTHORITY-CHECK, suppress COMMIT, or skip the SY-SUBRC check; (2) the OFFLINE greenfield linter — gf-inv-authcheck-no-subrc, gf-x-authcheck-subrc-after-write (gate-runs-too-late ordering), and gf-inv-commit-in-loop are all error-level; (3) Gate 7 abap-security-reviewer, diff-based against a baseline, which BLOCKs if a managed/unmanaged save 'no longer reaches COMMIT ENTITIES / the save sequence.'

ABAP CDS modelling

How the harness models data in ABAP CDS: a two-layer view-entity model (interface ZI_* → projection ZC_*), RAP composition trees, semantic/UI annotations, and the released-base extensibility contract. This section separates the SAP CDS facts from what the harness actually generates (from a fill-in template), lints offline (greenfield GF-2 linter), diagnoses (analyser rule packs), and gates (live ATC, variant ABAP_CLEAN_CORE_DEVELOPMENT).

Why does the harness generate CDS view entities (DEFINE VIEW ENTITY) only, never the legacy DEFINE VIEW / @AbapCatalog.sqlViewName form?
SAP fact: a legacy DEFINE VIEW is a DDIC-based CDS view that generates a separate managed database SQL view (declared via @AbapCatalog.sqlViewName) as its runtime object; the modern DEFINE VIEW ENTITY is the runtime object itself (no shadow SQL view), is the only form released for ABAP Cloud development, and carries improved session-variable, provisioning and extensibility semantics. The harness bakes this as prime directive P3: the CDS template's HARD RULES forbid the classic form outright, and both generated layers are 'define view entity' / 'as projection on'. Enforcement is dual — the greenfield GF-2 linter emits gf-cds-classic-view (severity error) on any .ddls source whose text has DEFINE VIEW not followed by ENTITY, and the analyser flags talos-cds-legacy-sqlview (priority-2) on any @AbapCatalog.sqlViewName. Because the GF-2 finding is an ERROR, it hard-fails the offline lint→regenerate loop (lintAbapCloud blocks on error) before any SAP round-trip.

What is the interface (ZI_*) vs consumption/projection (ZC_*) layering, and how strictly does the harness hold it?
SAP/VDM fact: the interface view is the reusable, UI-agnostic data-model layer (keys, compositions, associations, authorization posture, semantic annotations — no @UI); the consumption/projection view sits on top as 'projection on' the interface, carries the @UI annotations and is what the OData service exposes. The harness template is explicitly two-part: Part 1 ZI_<Entity> holds the composition tree, the association to parent, @AccessControl and the explicit field list with NO @UI; Part 2 ZC_<Entity> is 'as projection on ZI_<Entity>' with the @UI facet/lineItem/identification annotations plus redirected associations. Note this rich layering check lives in the analyser (brownfield/modernise track), not in the greenfield GF-2 linter.

How does the model distinguish compositions, associations, and the to-parent, and does the harness enforce the RAP composition rules?
SAP/RAP fact: a composition is an owning whole-part relationship — the child's lifecycle is bound to the parent (it cannot exist without it, and the composition root defines the BO's transactional boundary); an association is a non-owning reference (to a master/value-help/text entity). Every child in a composition tree must declare exactly one 'association to parent', and the root omits it. The harness template encodes this: 'composition [0..*] of ZI_<Entity_Child> as _<Child>', 'association to parent ZI_<Entity_Parent> as _Parent', and an optional value-help 'association [0..1] to <released_text_source>' — with the projection using 'redirected to composition child ZC_*' / 'redirected to parent ZC_*' so the exposed OData tree stays inside the ZC_ layer. The template also wires the interface view as the BDEF's root ('define behavior for <ZI_Entity>'). On cardinality, the analyser flags an uncapped $expand-able 'composition [0..*]' without a maxItems cap (talos-cds-expand-no-cardinality-cap, ABAP-PERF-22). The greenfield GF-2 linter does NOT yet build the cross-DDLS CDS composition/association graph — that entity-graph cluster is explicitly roadmap in the GF-2 exceed backlog.

What exactly is Clean Core "Level A" in this harness — is it a SAP term or a harness invention?
Clean Core is SAP's principle of keeping the digital core upgrade-stable by extending only through released public APIs and sanctioned extension points, never modifying SAP objects. "Level A" is the top of the harness's own internal A/B/C/D spine (the oracle): A=released, B=classicAPI (advisory/P3), C=deprecated (warning/P2), D=notToBeReleased or noAPI (blocker/P1); anything unlisted is 'unknown'→needs_review, which INDETERMINATE-blocks a Level-A target. P1 requires every generated/modified object to be Level A — released APIs plus sanctioned extension points only, zero modifications, zero source-code plug-ins — while brownfield source may sit at any level (that is diagnosis, not failure).

Brownfield analysis + modernisation (offline analyser → moderniser factory)

This subdomain covers the harness's two offline engines: the standalone analyser that builds a code property graph and scores S/4HANA readiness, blast radius, and tech debt into a single analyser-findings.json, and the moderniser factory that consumes that document and drives each legacy object toward a Clean-Core Level-A artifact set. Both run engine-to-engine with no MCP servers and no DEV credentials; the offline path deliberately never reaches GREEN because activation and ABAP Unit need a live tier.

How does the analyser build the code property graph — parser, node model, edge model?
@abaplint/core parses the abapGit bundle into a Registry; analyzeRegistry then registers EVERY object as a node first (id/kind/object/namespace, first-write-wins on kind so an in-bundle CDS entity is never mis-kinded 'table' by a consumer that parsed first), then walks resolved references plus statement-level and DDIC/RAP edges (call-method, PERFORM/form, call-function, get-badi, authority-check, inherits, consumes-cds, includes). Nodes are keyed by id and deduplicated; edges are deduplicated by the source|target|kind triple; adjacency is indexed both ways so blast-radius BFS walks predecessors and successors in O(1) per node. Node/edge shapes follow .claude/schemas/analyser-findings.schema.json — this is a genuine CPG, not a call-list.

How does the analyser score S/4HANA readiness versus ABAP Cloud readiness, and why are they different numbers?
SAP fact: on S/4HANA on-prem the classic patterns (CALL FUNCTION, classic ALV, OPEN DATASET) still run, so the real on-prem blockers are deprecated/removed SAP objects and modifications to SAP standard; ABAP Cloud is stricter because it is released-API-only, so those classic patterns plus non-released (classicAPI) APIs and clean-core/security violations all block. How is blast radius computed, and what does 'affected' actually mean given edge direction?
Dependency edges point dependent→dependency (A calls B ⇒ edge A→B), so the objects 'affected by a change to T' are the transitive PREDECESSORS of T's nodes, aggregated up to their owning objects. It is a depth-limited BFS (default 3 hops) with a visited set so cycles terminate and dense graphs don't explode, and the result is tiered by affected-object count: ≥50 critical, ≥20 high, ≥5 medium, else low. The thresholds are deliberately coarse (the code itself notes 'refine against corpus calibration'), so treat the tier as a triage signal, not a calibrated metric.

What is the Karpathy ratchet here, and how can a first rewrite ever pass if 'quality only tightens'?
The ratchet has one hard, non-overridable conjunct (atc_p1==0) plus two only-tighten baselines: accepted WARN goes only-down and coverage goes only-up. This harness vs a copilot like SAP Joule

Different categories. SAP Joule for Developers is an IDE-native AI copilot — a purpose-built LLM in ADT that generates code & unit tests, explains code, and explains ATC findings with fix guidance; the developer drives and judges. This harness is an autonomous, enforcing SDLC pipeline: a separate evaluator renders merge-blocking verdicts against hard SAP-native gates the generator cannot bypass. Correctly weighting Joule's edge

Two things people assume favour Joule actually don't. Setup: this harness is an install-and-go Claude Code plugin, and its offline pipeline needs no SAP system at all. ADT integration: the harness ships its own mcp-adt-bridge + sap-adt-sidecar doing real ADT (discovery, auth, CSRF, lock→PUT→activate) — the same developer-tools services Joule rides. So neither is a Joule differentiator.

Joule's genuine advantages are narrower and are buy-vs-build advantages: it is SAP's own supported product (no engine to maintain), backed by a model trained on SAP's private code corpus, and it is the lowest-friction option for a single developer already in ADT. What none of those close is the decisive gap: Joule is manual and one object per prompt, with the developer as the only judge; the harness plans and drives an entire dependency-ordered modernisation autonomously, behind independent, fail-closed gates that block what a copilot leaves to the developer to catch. For a solo in-IDE task, reach for Joule. For an enforced, auditable, at-scale pipeline, that is precisely what this harness is.
